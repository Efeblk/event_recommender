# Local preparation schema

From `web/`, use `npm run catalog:start`, `npm run catalog:import`, `npm run catalog:verify`, and `npm run catalog:verify:offers` with Node >=22.13. Scripts use only the task-owned local Docker database, bind to loopback, and make no AI calls. Existing frozen prepared snapshots are required; this milestone does not collect or enrich new source evidence. Start initializes the schema only when absent, validates the known contiguous migration history, then applies pending migrations. It preserves installed functions and verifies migrations 012/013's complete seal/publisher/validator bodies; drift or incompatible markers fail closed. Frozen import backfills only new initial offer revisions. `catalog:verify:migration-replay` checks these contracts in a disposable database. The full-catalog `catalog:verify:bulk-publication` additionally requires the preserved ignored frozen dump/fixtures; it is a local qualification command, not a generic CI fixture.

`schema.sql` creates the isolated `biplan` PostgreSQL schema and requires PostgreSQL 17 with PostGIS, pgvector, and `pg_trgm`. It never drops application data and refuses incompatible base metadata. Use the initializer rather than replaying this historical file over a migrated database: earlier function definitions can overwrite later ones.

Load normalized JSON with `SELECT biplan.ingest_prepared_payload($1::jsonb)`. The import boundary accepts the `CatalogKnowledgeBundle` fields (`schemaVersion`, `normalizerVersion`, `inputProvenance`, `productions`, `venues`, `sessions`, `providerOffers`, `sourceObservations`, `sourceClaims`, and `evaluations`) plus optional `works` and `documents` arrays. Callers remain responsible for deterministic IDs, normalization, hashes, and vector generation; exact provider records are retained from `providerOffers[].raw` and `sourceObservations[].raw`.

Publication rows are immutable snapshots. Validate a candidate and set its validation fields before calling `biplan.activate_publication(candidate_id, expected_previous_id)`. The function locks the pointer, checks its previous-version guard, mandatory counts, embedding profile, and canceled/missing sessions, then switches the singleton pointer atomically. `publication_evaluations` pins the current evaluation versions, including pending entries. Workers use `biplan.claim_preparation_jobs(worker_id, batch_limit, lease_interval)` and `biplan.complete_preparation_job(job_id, worker_id, expected_fencing_token, checkpoint)`; completion rejects expired or replaced leases.

The strict legacy provider-offer guard remains a **frozen import replay constraint**. Migration `002-offer-revisions.sql` separates stable `offer_identities` from immutable `offer_revisions`; `publication_offers` pins exact revisions rather than resolving the current pointer. Version-3 import manifests require exact offer counts. Validation checks raw snapshot coverage, session membership and acceptance status, and is enforced when publications transition to validated/active states.

Incremental offer writes use `biplan.accept_offer_revision(payload, expected_current_revision_id)`. Required payload fields are `revisionId`, `offerId`, `sessionId`, `provider`, `providerRecordId`, `observedAt`, `contentHash`, and object `sourcePayload`. Optional fields preserve source/session IDs, tier, link, currency, price/priceMinor/feeMinor, priceKind, availability, sourceUpdatedAt and validity dates. A revision ID identifies an immutable observation request; fresh checks need new revision IDs even if facts are unchanged. The function returns accepted/held_stale/held_conflict, reason, revision/current IDs and an idempotent flag. Server hashes independently cover raw and normalized facts; ID reuse with changed input fails. Callers own normalization and authoritative source timestamp interpretation.

Acceptance locks initial and existing identities, checks the expected previous revision and source-clock policy, and atomically stores the revision, advances the head, queues content-addressed derivation and emits revision-specific outbox work. Equal source versions with conflicting facts are held; older observations at an equal/unversioned clock cannot regress freshness. Missing source clocks against versioned current data are held. These rules order one provider's observations and do not establish cross-provider truth. Replay returns the original decision without rewinding a subsequently advanced head.

Derivation jobs reuse identical content, while **every accepted revision emits an outbox event**, including fresh identical checks and A→B→A reversions. Publication consumers must process these events independently of derivation cache hits.

Migration `003-workers.sql` implements bounded, filtered preparation/outbox leases, worker-bound fencing/replay, durable checkpoints/attempts, explicit retry and exhausted-lease cleanup. `npm run catalog:work` executes the local worker; `npm run catalog:verify:worker` exercises the actual worker/API in a disposable database, then removes that database. Claims support only offer stage version 1 and the offer-revision topic; other work stays untouched. Defaults process at most eight jobs and eight events, alternating queues and claiming one item at a time. `CATALOG_WORKER_MAX_JOBS`, `CATALOG_WORKER_MAX_EVENTS` and `CATALOG_WORKER_TIME_MS` adjust bounded limits. The time setting stops new claims; an in-flight operation may finish after that deadline. Interruptions remain retryable for a later invocation; the worker does not loop on a failed item. Computation happens outside database transactions.

For unchanged frozen offers, `CATALOG_WORKER_ENQUEUE=8` queues at most eight missing price derivations before the invocation; default enqueue is zero. SQL also exposes `enqueue_missing_offer_preparation_jobs(limit)`. This is replay-safe and emits no canonical-change notification. Example from PowerShell in `web/`: `$env:CATALOG_WORKER_ENQUEUE='8'; npm run catalog:work; Remove-Item Env:CATALOG_WORKER_ENQUEUE`.

The worker derives stable normalized price facts with decimal-string minor units and preserves unknown fees, stock, promotions and quality. SQL verifies the result against its immutable accepted source before atomically storing `offer_derivations` and completing the leased attempt. Local completed attempts record zero external-call cost units. It does not cache current freshness or time-dependent eligibility.

Internal outbox delivery atomically records an exact-revision `publication_refresh_requests` row and marks delivery. `npm run catalog:refresh` consumes these requests using migration `004-publication-refresh.sql`; `npm run catalog:verify:refresh` verifies real JS/SQL execution in a disposable database. Defaults process up to eight requests and stop new claims after 30 seconds (`CATALOG_REFRESH_MAX_REQUESTS`, `CATALOG_REFRESH_TIME_MS`). Failures stop the invocation; explicit retry/interruption can resume later. In-flight work may finish after the claim deadline.

The consumer captures every current offer head for the affected existing session, even when its request references an older revision. It copies an immutable publication, rebuilds that session's snapshot/pins, validates, atomically switches the guarded pointer and completes the fenced request. Matching heads **and** matching projections coalesce without a new generation. Expiry/freshness changes can invalidate projected pricing. Unaffected sessions remain frozen: the manifest identifies only the affected session/head set and does not claim global freshness. Missing newly discovered sessions are explicitly blocked and need the canonical preparation path.

Refreshed snapshots have `offerTermsVersion:1` and authoritative typed `offerTerms`, plus exact raw `offers` as evidence. A raw object is not a guaranteed `EventOffer`. `offerSummary` and compatibility display fields exclude sold-out/unavailable, invalid-time, stale/future and unknown/contradictory-price offers; the projection policy uses a 72-hour freshness window. Unknown fees remain unknown and display prices are not hard-budget totals. Completed price/value/comparative evaluation pins are conservatively removed with manifest invalidation IDs, keeping historical rows and pending evaluations; optional score recomputation does not block critical offer updates. Price/availability changes reuse unchanged text document/vector references.

`current_publication_offer_status(publication,session,checked_at,max_age)` reads pinned/current IDs and reasons without substituting generations. `availabilityUsable` (also `usable`) checks canonical identity/time/status, complete head-set consistency and at least one fresh/effective available offer. `verifiedTotalEligible` additionally checks a known exact TRY single-ticket price and fee; it does not prove group stock, adjacent seats or every user constraint. Request dates, quantities, budgets, accessibility and other source requirements still need their own checks. Revalidate immediately before rendering, including after rollback. The opt-in PostgreSQL HTTP backend performs these mandatory checks; deployed snapshot traffic has not cut over.

Canonical creation/correction and pinned retrieval are implemented locally. The Node HTTP backend opts in with `CATALOG_BACKEND=postgres` and an explicit PostgreSQL connection; deployed services still use the snapshot backend. Verified checkout fees, live enrichment, calibrated quality scoring, timed expiry scheduling and managed cutover remain outstanding. Local Docker commands require the ownership label; injected query adapters can use the same guarded SQL APIs without Docker.

Migration `005-canonical-preparation.sql` accepts new identities and canonical corrections with immutable source claims, occurrence bindings and adverse-evidence disputes. `catalog:canonical:source` validates normalized records before lookup and retains quarantine decisions. Its file checkpoint has an exclusive consumer lock; a crash after database commit reuses the deterministic request. The 005 per-record publisher remains an isolated legacy verification path.

Migration `006-batched-publication.sql` is the production preparation contract: begin a run with immutable scope/providers/horizon/input hash, accept bounded normalized observations, seal with truthful provider inventory, prepare documents, then publish one coherent generation. `catalog:batch:work -- BATCH_ID` prepares up to 100 jobs within a 30-second claim budget and attempts publication only when every required job is complete. It never reconstructs coverage from old aggregate checkpoints. Held or quarantined mandatory observations block publication; optional missing vectors retain lexical coverage. Storage admission requires an explicit administrator configuration and never deletes evidence or rollback versions. Current-head checks can withhold older cards while a batch is preparing.

`catalog:verify:batch` uses synthetic provider inventory in a disposable database to check 20/100-record publication behavior; it makes no live coverage claim. `catalog:verify:roles` verifies actual effective restricted privileges. `roles.sql` is a separate administrative install step after all reviewed migrations, never an automatically applied generic migration. Neither local verification nor a Linux preparation image establishes Cloud SQL/IAM/recovery readiness.

`catalog:verify:managed-admin` tests installation and migration/role replay as a separate `NOSUPERUSER CREATEDB CREATEROLE` database owner in a disposable database. Local extensions are installed separately as `postgres`, so managed extension privileges remain unverified. The installer intentionally inherits and can set the NOLOGIN owner role; neither application login receives that membership. Schema ownership transfer grants the owner database `CREATE` only within the installation transaction and revokes it before commit. Preserve this dedicated administrator's authority for later reviewed migrations; an unrelated administrator must acquire explicit role-administration authority rather than bypassing the guard. These requirements follow PostgreSQL 17's [role creator membership rules](https://www.postgresql.org/docs/17/role-attributes.html) and [schema ownership rules](https://www.postgresql.org/docs/17/sql-alterschema.html). Cloud SQL [does not give its administrator true superuser privileges](https://docs.cloud.google.com/sql/docs/postgres/users); create application logins through this reviewed SQL instead of a default built-in-user workflow that can add elevated memberships.

`catalog:batch:source -- BATCH_INPUT.json` consumes `{header,records,collectorCoverage}`. Set `header.inputHash = batchInputHash(envelope)` after filling every other field. The header includes `batchId`, `collectionRunId`, `scope`, sorted `providers`, and UTC `horizonStart`/`horizonEnd`; the coverage requires `finishedAt`, `complete`, `failedPages`, `unvisited`, and each provider's separate `discovered`, `verified`, `retired`, `quarantined`, `unvisited` and `failedPages` counts. This input must come from preserved collector inventory evidence; do not fabricate it from the record array. Defaults accept eight new records, adjustable to 1..100 through `CATALOG_BATCH_SOURCE_MAX_RECORDS`. One bounded SQL checkpoint read skips durable items without repeated identity lookup; seal occurs only after the whole hash-locked input is accounted for. The CLI is local; `ingestBatchSource` supports injected stores for a future cloud collection boundary. It never publishes.

The portable preparation image is built from the repository root with `docker build -f web/deploy/Dockerfile.preparation .`. It accepts only `prepare SEALED_BATCH_ID` or `publish SEALED_BATCH_ID`, uses a non-root Node 22 runtime and the PostgreSQL dependency closure, and defaults to a 30-second SQL timeout. Provide the explicit database connection/password through protected settings and a Cloud SQL attachment. Cloud Run Job settings must enforce one task, parallelism one and `maxRetries=0`; exit 2 means bounded unfinished work or publication not ready and requires an explicit subsequent execution. This image does not collect, accept, seal, migrate or generate embeddings. No job has been deployed yet.

`npm run catalog:source -- INPUT.json` accepts normalized collector EventRecord arrays or report pages. Defaults process at most eight new observations; `CATALOG_SOURCE_MAX_RECORDS` accepts 1..100. Repeated receipt decisions skip database calls and advance to unfinished records. The default receipt is the ignored `web/work/catalog-foundation/source-replay.json`; an explicit second argument chooses another receipt. Run only one consumer per receipt file. File checkpoints are not in the SQL acceptance transaction: crash-after-commit recovery reuses deterministic observation IDs and the existing idempotent CAS API. Malformed, unmatched/ambiguous, new-session and canonical/search-fact changes quarantine with the original record. This path does not infer merges, create sessions, update documents or collect provider pages. Current normalized records supply checkedAt, aggregate starting prices and availability; provider update clocks, exact checkout fees, tier/stock guarantees and promotions are unknown.

`npm run catalog:search -- --query "seramik atölyesi"` reads the active publication through one SQL statement, ranks the complete eligible set and revalidates every selected card's exact offer. This is a local lexical shortlist, with no Jev relevance judgment. The injectable TS contract also supports compatible cached 1024D vectors with an explicit query profile. Legacy publications obtain typed terms from immutable revision pins; raw JSON cannot supply price facts. Unknown fees/starting prices do not prove a hard budget. The reader never substitutes a newer generation when final checks fail. Structured `--filters` JSON and explicit `--publication` are supported; `--at` is historical replay and is recorded as such, not current availability evidence. CLI receipts include provenance and all returned cards.

`npm run catalog:verify:flow` exercises ingestion, replay, worker/outbox, refresh, pinned reads, null attendance representations, exact/unknown group costs and concurrent cancellation in a disposable database. `npm run catalog:verify:read` audits every frozen main-catalog snapshot/document/offer pin and checks current-time local shortlists. Frozen inventory remains historical; neither command establishes live provider freshness, Jev relevance, cloud performance or launch readiness.

## Page and record receipts

Migration `007-page-receipts.sql` extends the migration 006 batch contract. The record-only `catalog:batch:source` input above remains a legacy v1 fixture path; its normalized-record counts cannot substitute for detail-URL coverage or qualify managed readiness.

`catalog:page-batch:source -- REPORT.json BATCH_ID COLLECTION_RUN_ID` adapts a preserved collector report to the v2 boundary. `CATALOG_PAGE_BATCH_MAX_ITEMS` limits each invocation to 1..100 new pages/records (default eight). One bounded checkpoint read skips durable work; pages are stored before their records, and sealing occurs only after the hash-locked input is accounted for. Original clocks, normalized page hashes, any distinct raw-response hash and zero-record retired/quarantined pages remain evidence. Carried snapshot records are not new observations. URL inventory counters and submitted event-record counters use separate units. The adapter/store are injectable; this CLI requires the owned local database and never publishes.

Explicit collector cycles opt in with `--cycle-id`, `--cycle-scope full|incremental`, `--cycle-started-at`, `--horizon-start`, `--horizon-end`, `--geography Istanbul` and `--listing-config-hash`. Use `--begin-cycle` once to start a new cycle; subsequent invocations must repeat its exact scope. Derive the hash with `collectionListingConfigHash` from the selected provider/listing configuration. Reports retain the complete known URL identity inventory, including retired/unresolved URLs. Full completion requires exhausted discovery, every declared URL resolved in that cycle, matching durable page/record evidence and unexpired source freshness. Historical reports retain unknown original horizons and remain `legacy_incremental`; replay cannot make them complete.

Migration 007's original behavior conservatively blocks negative/disappeared page families. Migration `008-offer-evidence-projections.sql` resolves ordinary offer disappearance through immutable publication evidence pins: unsupported offers have unknown effective price/availability, while a separately supported compatible offer can supply a card. It rebuilds page-affected sessions even when the page returns zero records, preserves raw revisions, and reuses unchanged canonical documents. Mandatory identity/time/venue/source-clock conflicts still block publication. New projection generations mask untouched legacy offers without page proof; do not cut over before replacement coverage is verified. Final validation checks the selected revision/page dependency and family integrity, without switching offers or generations. Verify with `catalog:verify:offer-projections`; the earlier 007 checks remain separate historical contract tests. The portable Cloud Run preparation entry requires v2 receipts. Repeating an already published batch reports durable completion without claims or pointer activation.

## Portable source ingestion

`web/deploy/Dockerfile.source-ingestion` packages a separate nonroot source Job. Its entry takes `BATCH_ID OBJECT_KEY GENERATION SHA256`, with `GCP_STORAGE_BUCKET` and protected PostgreSQL settings. The key must be `staging/preparation/sources/<SHA256>.json`. An operator must first upload the complete v2 envelope create-only; the current snapshot checkpoint is not a substitute. Managed upload, Job admission and bounded synthetic ingestion/preparation/publication are verified in the [September 30 evidence](../../docs/gcp-postgres-staging-validation-2026-09-30.md); continuous live collection and complete provider coverage remain unverified.

Before opening PostgreSQL, the Job verifies the exact generation, bounded size, CRC32C, SHA-256, batch identity and complete envelope. Storage retries are disabled. `CATALOG_SOURCE_LIMIT` controls 1..100 new page/record items per execution (default eight); the artifact has a hard 32 MiB ceiling. The preserved 1,864-page/8,004-record historical envelope is about 13 MB and remains incomplete. Each execution currently downloads and validates the complete envelope and reads its checkpoint set; managed throughput and cumulative cost must be measured before a live full-catalog run.

The process deadline defaults to 90 seconds; PostgreSQL uses two connections and a 30-second statement timeout. Configure one task, parallelism one and `maxRetries=0`. Exit 0 means a coherent seal or verified replay of completed ingestion, exit 2 means bounded remaining work or a blocked seal, and exit 1 means failure/interruption. It never prepares or publishes a generation. Repeated executions must retain the same artifact generation, SHA and batch identity. The dedicated preparation identity receives only prefix-scoped artifact reads and its own database secret.

From `web/`, `npm run catalog:source:upload -- ENVELOPE.json BATCH_ID` validates the full envelope before opening Storage, writes with `ifGenerationMatch=0`, then reads back the pinned generation with CRC32C/SHA verification. A lost write response or existing object is successful only after this complete readback. Set `DEPLOYMENT_ENV=staging`, `BIPLAN_GCP_PROJECT=biplan-staging-efeblk` and `GCP_STORAGE_BUCKET=biplan-staging-efeblk-biplan-staging-data`. The operator needs create/get permission for this prefix; this command adds no IAM and never grants the collector or Job storage writes. Request retries are disabled, requests are bounded to 20 seconds by default and the command has a 60-second abort deadline. An interrupted create may still commit; rerun the same immutable input to verify it rather than overwriting it. Keep raw envelopes under ignored `web/work/`.

`npm run deploy:postgres:job:render -- SETTINGS.json` is offline only. It writes an immutable JSON manifest under ignored `web/work/catalog-foundation/job-manifests/`, prints its path/hash, and performs no deployment or execution. Settings contain `mode` (`source`, `prepare` or `publish`), string `projectNumber`, immutable `image` digest, 40-character `revision`, numeric string `secretVersion` and `batchId`. Source mode additionally takes the fixed staging `bucket` and the upload receipt's `artifact: { key, generation, sha256 }`; other modes reject those fields. Use the expected `biplan-source-ingestion` or `biplan-preparation` image in staging's Artifact Registry. Never put a password in settings. The manifest binds the approved Cloud SQL connection, preparation service account and numeric secret version, one task/parallelism, zero retries, 1 CPU/1 GiB, a 180-second task timeout and a 90-second process deadline. It follows the [Cloud Run v1 Job schema](https://docs.cloud.google.com/run/docs/reference/yaml/v1) and [secret reference annotations](https://docs.cloud.google.com/run/docs/configuring/jobs/secrets). Managed API admission remains a staging acceptance check.

After authentication, first read back the approved project, billing/resource state and saved Terraform plan. Deploy a rendered manifest only against `biplan-staging-efeblk` in `us-central1`, preserve its hash/image/secret provenance, then execute one bounded Job and review its receipt before any repeat. Source ingestion, preparation and publication remain separate actions. No scheduling, automatic execution, paid inference or public rollout is enabled by these tools.

Publication uses a separate worker-only SQL profile: short controls use 5-second server/10-second driver limits, while the publication statement has 60/65-second limits. The process and lease default to 120 seconds; the Cloud Run task remains 180 seconds with zero retries. Admission requires 110 seconds remaining before checkout and 95 after setup, including failure/reset/close reserve. Insufficient time stops before claiming or records a retryable bounded failure. Session timeout resets to 5 seconds; a failed reset destroys the connection. `publicationSqlMs` measures only the SQL call. The 5-second close wait does not cancel active SQL; the task limit remains the hard backstop. Source/preparation and HTTP keep their separate limits.

Receipts, verification artifacts and local database settings are ignored under `web/work/catalog-foundation/`. See [implementation checkpoint](../../docs/catalog-enrichment-implementation.md) for verified results and remaining scope. Do not print the local password file.
