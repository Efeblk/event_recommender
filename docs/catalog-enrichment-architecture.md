# Catalog enrichment architecture

Bi’ Plan's enduring product goal is to continuously enrich and evaluate event data so it can give fast, inexpensive, reliable recommendations. Search consumes that knowledge; collection, identity resolution, evidence, scoring, and offer economics are first-class parts of the product.

Decision date: September 29, 2026. Status: selected target architecture and implementation workflow; migration is not implemented by this decision. Third-party membership and student discounts are possible future integrations, not verified available offers. Architecture choices give no preference to the existing implementation. This decision does not activate subscriptions, resources, partner integrations, or public deployment.

## Architecture decision

Build one modular Node/TypeScript codebase with separate HTTP and durable job entry points. Use PostgreSQL as the authoritative store for canonical entities, explicit relationships, source observations, offers, derived evaluations, job state and publication metadata; PostGIS for geography; pgvector for semantic retrieval; PostgreSQL full-text/trigram tools for lexical and entity matching. Keep original provider responses and reusable artifacts in private object storage. Canonical tables and a versioned denormalized search projection are different models in the same database, with one publication contract.

On GCP, use Cloud Run for HTTP, scheduled Cloud Run Jobs for bounded preparation, private Cloud Storage for artifacts, and Secret Manager for credentials. Cloud SQL for PostgreSQL is the preferred managed GCP database host, subject to a concrete cost/configuration review before provisioning. Exact region, tier, availability, connection capacity and backup retention are implementation decisions requiring measured sizing; they are not selected or purchased here. Keep the HTTP/job/database regions close and bound connection pools against maximum instances. Cloud Run scaling to zero does not imply the database is free or scales to zero.

Start with one database and batch jobs, not microservices, a separate graph/vector/search engine, an always-running AI worker, or a universal promotion-rules platform. Logical modules isolate collection adapters, canonicalization, enrichment, evaluation, offer rules, publication and request serving. `collector/` owns preparation and publication; `web/` owns request interpretation, retrieval and presentation. Share versioned contracts and deterministic rule code rather than duplicating them. No preparation is detached from an HTTP request as unawaited work.

## Research and rejected alternatives

The decision follows the dominant workload: continuously maintained, source-backed entities; dated sessions; geography; constrained offer economics; and semantic/lexical ranking. It is not a measured universal speed claim. The previous local graph experiment does not compare a fresh PostgreSQL implementation and is not decision evidence for production latency or human-query relevance.

| Option | Finding and decision |
| --- | --- |
| PostgreSQL + extensions | Primary choice. Relational constraints, explicit associations, spatial filtering, lexical matching and vector ranking fit the required workload in one operational store. [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html), [PostGIS indexes](https://postgis.net/documentation/faq/spatial-indexes/), [trigram matching](https://www.postgresql.org/docs/current/pgtrgm.html), [pgvector](https://github.com/pgvector/pgvector). |
| Neo4j + vectors | Capable alternative, not inherently worse or incapable of filters. Current `SEARCH` supports restricted vector-index property predicates; variable-length traversals are a strong feature. Choose it when such relationship exploration becomes a frequent core query and representative tests justify it. Relationship count and easier diagrams alone are not decisive. [Filtered vectors](https://neo4j.com/docs/cypher-manual/current/clauses/search/), [paths](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-paths/). |
| Dedicated vector/search tier | Qdrant supports filter-aware vector retrieval, but would add a replicated representation and consistency work alongside the canonical store. Add a projection when measured volume, concurrency, recall or lexical requirements warrant independent scaling. [Qdrant indexes](https://qdrant.tech/documentation/manage-data/indexing/). |
| Firestore | Do not choose as the canonical enrichment/search store. Standard document-query constraints are a less natural fit for evolving relational and offer-rule workloads. Do not claim Firestore has no vector or text capabilities: vectors are supported and native text search is currently an Enterprise preview. Existing coordination is deployed state, not a reason to preserve its architecture. [Query limitations](https://cloud.google.com/firestore/docs/query-data/queries), [vectors](https://docs.cloud.google.com/firestore/native/docs/vector-search), [text search](https://docs.cloud.google.com/firestore/native/docs/text-search). |
| Spanner Graph | Relational, graph and vector capabilities are attractive, but no product requirement establishes the need for a distributed primary database. Trial availability is not permanent free production economics. Revisit for demonstrated distributed writes/availability requirements and an acceptable cost model. [Spanner capabilities](https://cloud.google.com/spanner), [pricing](https://cloud.google.com/spanner/pricing). |

PostgreSQL does not imply unlimited capacity or automatic horizontal write scaling. Measure query plans, indexes, database resources and concurrency; scale vertically/read replicas where appropriate before adding a new engine. Cache only with version/freshness-safe keys. Choose hosting on total cost, including compute, storage, index memory, backups, network and operational work, rather than free trial labels or unequal minimum tiers. Cloud SQL supports the needed extensions but capability does not prove an adequate machine size. [Cloud SQL extensions](https://docs.cloud.google.com/sql/docs/postgres/extensions), [pricing](https://cloud.google.com/sql/pricing).

Cloud Run jobs can be scheduled independently of HTTP serving. Idle service instances can terminate, so request-lifetime background work is not a durable preparation system. [Scheduled jobs](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule), [billing/lifecycle](https://docs.cloud.google.com/run/docs/configuring/billing-settings).

## Domain boundaries

| Entity | Responsibility |
| --- | --- |
| Work | Underlying play, composition, or other identifiable work; author, themes, and cultural significance. Optional for activities without an underlying work. |
| Production or activity | The actual adaptation, show, workshop, or experience; cast, director, organizer, and production-specific evidence. |
| Session | A dated occurrence or admission window at a venue; timing and attendance requirements. |
| Venue and place | Stable venue identity, coordinates, aliases, neighborhood/district membership and its evidence. |
| Person and organization | Performers, creative teams, organizers, ticket providers, and possible promotion sponsors; explicit relationships and roles. |
| Provider offer | Source listing, ticket tier, price/currency, fees when known, availability and source IDs/links for a session. |
| Promotion | Separately sourced benefit with validity, eligibility, applicability, redemption, limits, and stacking rules. |
| Observation or claim | Original evidence, source, observation time, subject, support/conflict status, and refresh policy. |
| Evaluation | Versioned scores/features derived from referenced evidence under a defined rubric. |
| Search publication | Prepared retrieval records and embeddings tied to a coherent published catalog version. |

Preserve work, production, and session distinctions. The reputation of a classic work does not establish the quality of a particular adaptation. Identity merges require supporting evidence and retain original provider records.

## Enrichment and evaluation

Each enrichment adapter contributes source-backed claims with stable subjects and provenance. Preserve event time separately from observation/ingestion time, source update time and effective claim validity when known, source record ID and content hash. Fetching a claim later does not make it more authoritative. Current canonical fields are resolved views of observations, not overwritten history. Conflicts, unknown values, failed refreshes, staleness and explicit cancellations remain distinct. Source precedence must be field-specific and documented; disputed identity or mandatory evidence is quarantined or withheld rather than guessed.

Use typed canonical fields and typed relationship tables for decision-critical data. Keep evolving provider-specific details in validated JSONB/observations; do not replace the whole model with opaque JSON documents or arbitrary subject-predicate triples. Do not infer a neighborhood from a district alone. Preserve location resolution evidence and precision; radius/boundary queries require usable coordinates and verified geographic definitions.

Refresh mutable offers and promotions independently from slower-changing work and person information; invalidate dependent data when its supporting evidence changes. Dependencies include identity mappings, normalizers, rule/rubric versions and comparison cohorts, not just a single source row. Expiry requires scheduled invalidation even without a new source observation; another offer's price can affect a cohort-relative value score. Each adapter declares its supported fields, source scope, freshness policy, limits and failure states. Collection failures cannot silently delete verified inventory; retained data still has to meet explicit freshness policy to support a claim.

Store separate dimensions such as production reputation, creative-team credentials, cultural significance, experience characteristics, and comparative value. Compare appropriate peer groups and retain review counts/source quality where applicable. Provider marketing, independent criticism and audience feedback are different evidence classes; syndicated copies are not independent confirmations. Account for rating scale, sample size and age before comparisons. Cast fame, a classic title, and promotional language cannot establish production quality.

Evidence coverage is separate from event quality: absent reviews do not mean a poor event. Model confidence is separate from evidence sufficiency and is not proof of truth. Avoid publication/composite rules that automatically bury new or independent productions. Quality weights and caps must be versioned and tested; do not invent permanent percentages before calibration. Base features can be reused, but relevance and effective value depend on the current request and applicable offer, without requiring persistent user memory.

Jev may classify and score supplied evidence using concrete rubrics. Code computes prices, eligibility and score composition. Preserve evidence references, rubric/model versions, component distributions and input hashes so unchanged evaluations can be reused and challenged. General evaluations must be tested against human-reviewed examples before influencing recommendations. A descriptive synopsis alone cannot establish production quality. Jev's Score primitive supports descriptive ordered levels and code-controlled composition, not proof of objective artistic merit. [Score](https://docs.typesafe.ai/primitives/score), [composite scoring](https://docs.typesafe.ai/patterns/composite-scoring).

Attach evaluations to the narrowest valid subject. Reuse work/person enrichment across productions, production evidence across sessions, and calculate location/timing/offer-specific suitability separately. Generate embeddings from versioned descriptive documents; volatile prices, stock, promotion eligibility and quality scores remain structured fields unless the document profile explicitly requires them. Changing a price or ranking weight should not require recreating unchanged semantic vectors. Reuse only exact content hashes and compatible endpoint/model/dimension/text profiles; query/document input types remain explicit.

## Future benefits and effective prices

Represent promotions separately from base ticket prices and general event quality. A promotion can apply to a provider, ticket tier, session, production, venue, or an explicitly maintained set of targets. Avoid a universal arbitrary rules language initially; use versioned, typed eligibility and applicability rules with an unsupported state for terms that cannot be evaluated.

Record membership/student requirements, applicable purchase channels, validity and event-date restrictions, benefit calculation, caps, minimum spend, ticket/group limits, redemption instructions, known fees, availability restrictions, and whether combination with other benefits is supported. Unknown terms cannot be assumed favorable. Preserve the source terms and their freshness.

Offer evaluation returns eligible, ineligible, or unknown eligibility. A user may declare relevant attributes for the current request without a persistent profile; self-declaration does not guarantee checkout acceptance. Unknown eligibility yields a conditional benefit, not a guaranteed discounted price satisfying a hard budget. Expiry and staleness are separate: an unexpired promotion can still lack recent verification. Record external redemption restrictions without pretending to know a user's remaining usage or operating an authoritative redemption ledger for purchases the application does not process.

Compute group cost per applicable offer and promotion rules, including caps and qualifying ticket counts. Two-for-one, fixed reductions, percentage discounts and cashback require different calculations. Cashback and non-cash rewards do not reduce the amount payable at checkout. Do not assume promotions stack or ticket inventory is sufficient; do not combine incompatible provider offers into a promised group price. Prices and savings should identify the tier and any unknown mandatory fees. An advertised starting price alone cannot establish a bookable group total; quantity and adjacent seating require separate evidence. Distinguish verified totals, estimates, conditional prices and unknown totals, and retain their calculation inputs.

## Publication and request flow

Preparation: collect immutable observations → validate/quarantine → resolve canonical identities → enrich and reconcile claims → calculate versioned features/evaluations and offer rules → prepare search records and cached embeddings → validate → publish a coherent version.

Preparation is incremental and resumable. Commit canonical changes and durable work/outbox records together; identify jobs by subject/input hash/stage version. Workers claim bounded batches with expiring leases and fencing tokens, keep external calls outside database transactions, checkpoint completed results, and reject stale completions. Duplicate execution must not create duplicate facts, publications or controllable charges. A provider timeout with unknown outcome is recorded as uncertain; do not promise exactly-once external inference or retry it blindly. Track every attempt under a cumulative budget and reconcile safely before reissuing paid calls.

Build a candidate publication manifest referencing immutable search records/evidence/evaluation/vector versions. Object storage and PostgreSQL do not share a transaction: write immutable objects first, verify them, then commit their references/manifest; failed commits can leave unreferenced artifacts for later cleanup. Use generation preconditions for conditional object operations. Validate counts, identity families, mandatory fields, provenance and embedding profiles before atomically switching the active publication pointer with a previous-version guard. Readers capture the publication ID once and use it throughout the request; successive reads at PostgreSQL Read Committed do not themselves ensure a coherent snapshot. Do not keep database transactions open while waiting on Jev/Voyage. Retain a previous valid publication for rollback and defer artifact deletion until readers/retention policy permit it. [Transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [object preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).

Optional enrichment or vector failures leave explicit unknown/pending status and a usable base/lexical path; they do not silently erase valid events or hold valid base publication behind editorial work. Broken required publication integrity blocks activation. Maintain a prompt critical-change path for cancellation, venue/time correction, price expiry and promotion withdrawal. Cancellation and mandatory offer/eligibility freshness may invalidate previously published candidates; apply that explicitly at final validation without blending unrelated generations into the ranking. A rollback cannot restore a canceled session's eligibility merely because its older snapshot contained it.

Request: preserve original input and prior request state → pin publication before catalog-dependent lookup → find candidate values/entities and bounded typo suggestions → Jev selects supported roles/intent → validate structured constraints and unresolved ambiguities → determine eligible sessions and supported offers → retrieve semantic and lexical candidates with prepared quality signals → shortlist up to 16 distinct candidates → Jev relevance judgment → recheck evidence, offer terms and freshness → return supported cards.

Code owns date/time resolution, party budgets, exact values and hard constraints. Relative dates use Europe/Istanbul and the request reference time. Normalize entity aliases without rewriting arbitrary words or numbers. A material unresolved budget/location/date interpretation triggers a focused clarification or a clearly labeled conditional alternative; never silently discard an exclusion. Pinning applies to each request, not the lifetime of an interaction; validate inherited entity references against the next request's publication. Current-request benefit attributes are optional and are not a saved user profile.

Generate/cache the query embedding under its exact profile. Retrieve across the eligible catalog with both dense and lexical branches; fuse ranks without treating raw heterogeneous scores as interchangeable. Prepared quality/value signals participate before final shortlisting while retaining relevance/diversity and an auditable path for events lacking optional evidence. Collapse equivalent recommendation identities without losing sessions/offers. Every shortlisted candidate must already satisfy mandatory rules; the final Jev step cannot excuse violations.

For restrictive filters with a manageable eligible set, use exact vector ranking. For broader workloads, use indexed approximate retrieval with appropriate filter planning/iterative scans and measured recall against an exact baseline. Never take a small global ANN result then filter it and conclude that no events exist. Sparse/missing vectors retain lexical eligibility. PostgreSQL approximate-index filtering and bounded iterative scans do not guarantee perfect recall. [pgvector filtering](https://github.com/pgvector/pgvector).

Do not collect pages, merge identities, enrich people/productions, evaluate the full catalog with Jev, or rebuild documents/embeddings during a search. Batch independent AI questions; add stages only when evidence or prior decisions require them. Cache by normalized intent, publication/profile, current benefit inputs and relevant time/expiry boundaries. Do not share a cache entry across different budgets or eligibility. Generate displayed reasons from source-linked facts/templates rather than inventing reviews; explain conditional prices, estimates and unknowns accurately.

Discount and quality signals influence candidate selection before final shortlisting. A score or conditional promotion never overrides a hard constraint. Return every distinct shortlisted event passing the support threshold, without a separate fixed count or unsuitable padding. Keep alternate candidates available. When Jev or Voyage fails, a deterministic fallback must preserve all mandatory rules and disclose its limitations; it must not invent a relevance score or hide pending indexing.

## Implementation sequence

The first usable milestone is the local schema/contracts plus representative prepared catalog and publication checks (steps 1–2). Full inventory, scoring qualification and managed cutover are later milestones; they do not delay that initial deliverable.

1. Define schema, canonical identity/evidence contracts, adapter interfaces and migration mappings; implement local PostgreSQL with the selected extensions and import a frozen representative sample. A sample is for validating the model, never a provider inventory/search cap.
2. Implement incremental preparation, hashes, durable work state and publication rollback; prove repeat execution, interrupted jobs, stale completions and reader consistency.
3. Build evidence-backed scoring rubrics using a diverse human-reviewed set, including new/unknown productions, classics with weak adaptations, famous cast without quality evidence and conflicting reviews. Preserve held-out cases; tune against reviewed outcomes, not model confidence alone.
4. Implement the request pipeline and synthetic benefit fixtures covering expiry, unknown eligibility, channels, fees, group limits, stacking and checkout-versus-cashback. Real benefit adapters follow only when their sources/terms are available.
5. Import the full supported inventory, reuse compatible cached vectors, and compare eligible IDs, identity families, recommendation quality and recall against frozen expected cases. Review every returned card and explain empty cases against actual inventory.
6. Propose concrete managed-database cost/connection/backup settings, then complete an authorized staged cutover with parity and recovery evidence. Keep current deployment adapters operating until the target is verified; historical staging evidence does not verify the new architecture.

Record p50/p95 end-to-end and per-stage latency, cold versus warm/cache hits, dataset size, concurrent load and hosting profile; cost per search and incremental enrichment including fixed database cost, failed attempts and cache hit rate; freshness/coverage; mandatory-constraint violations; eligible/semantic recall and source-backed ranking agreement. Exact vector-neighbor recall and missed suitable recommendations are separate metrics. Set concrete acceptance thresholds before evaluation and allocate calls within the task-wide authorized cumulative cost cap; a milestone or new ledger cannot reset that budget. Keep evidence and do not claim speed/cheapness/reliability from architecture names. Numerical targets remain provisional until benchmarked on representative traffic. Hard-rule and identity checks must have no known violations in acceptance cases; this is not a universal production guarantee. Approximate recall and subjective ranking require explicitly agreed measured targets. Held-out cases should span Turkish/English, genres, venues, prices and review-poor events, avoiding leakage from the same production between calibration and evaluation.

Reopen an engine decision only for a documented workload or feature change and representative evidence. Complex repeated path discovery can justify graph; independent retrieval scale can justify a vector/search projection; distributed write/availability needs can justify a distributed store. More entity types, enrichment sources, relationships, or hypothetical features alone do not trigger a new engine. Before public rollout, complete the existing launch/recovery/unattended-monitoring gates as well as the new architecture checks. No paid evaluation, deployment or new resource was performed for this documentation decision.
